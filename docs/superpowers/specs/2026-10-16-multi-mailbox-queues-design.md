# 双邮箱独立配置、任务隔离与双 Agent 使用设计

日期：2026-10-16。状态：待用户审阅；尚未实现或部署。

## 1. 目标与已确认范围

让两个 Agent 通过 CLI 同时操作邮件系统，支持两个独立发信邮箱；Gemini 补全不再占用邮件发送执行位。

- 每个启用邮箱独立配置、独立发送队列，各 2 个执行位，供正常发信和退信重试共用。
- Gemini 补全独立队列，4 个执行位；不增加单任务检索预算或自动重试次数。
- 收信与退信监控独立运行，不占用发送或补全执行位。
- CLI、交互预览页面、API 目录与两套 FMG Skill 同步更新，明确邮箱和模板选择。
- 保留当前限流、退信暂停、无效地址排除、用户发送确认和未知状态防重发规则。
- 现有 LIMINAL 固定正文、签名图和尾图不变，其他游戏的通用模板保留。
- 第二个邮箱地址、服务商和凭证尚未提供；开发使用虚拟配置，生产缺配置时禁用，不猜测或复用第一个邮箱凭证。

## 2. 当前实现与选择

已核对生产镜像 fmg-agent:economy-c414929：worker.py 中三类任务均进入 fmg_agent 队列，Worker 并发为 2；收信监控是同进程独立线程。Settings 只有一组 SMTP/Graph/IMAP 配置，预览从全局 smtp_from 取发件地址。

选择“一套 API/数据库 + 分角色 Worker + 每邮箱队列”。复用现有业务和存储，避免两套完整服务的数据分裂。只增加共享 Worker 并发不能隔离长时间 Gemini 调用；复制两套完整服务则增加授权、名单和回执管理复杂度，不采用。

服务拆分：

| 角色 | 队列/职责 | 并发 |
|---|---|---:|
| enrichment-worker | fmg_enrichment，仅邮箱补全 | 4 |
| mail-worker --mailbox ID | fmg_mail.ID，仅该邮箱发送与退信重试 | 每邮箱 2 |
| dispatcher | 单一调度进程，按类型与邮箱发布任务 | 1 |
| inbox-monitor | 每启用邮箱独立受控循环，读取各自文件夹 | 每邮箱 1 个循环 |

收信循环的网络超时和异常按邮箱隔离。某邮箱连接失败不得阻塞另一个邮箱的扫描。角色启动显式配置，普通 Worker 不隐式启动第二个调度器或监控器。

## 3. 邮箱注册与授权

新增服务端私有邮箱注册文件，路径通过配置提供。每项包含稳定 mailbox_id、enabled、发件地址、显示名称、允许模板 ID、发信方式、SMTP 主机/端口/TLS/认证、IMAP 主机/端口/认证/文件夹、Microsoft Client ID 和独立 Graph/IMAP token store 路径、发送间隔及原有安全配置。

- mailbox_id 使用受限的小写字母、数字和连字符，不允许路径字符；启用项不得重复使用同一规范化发件地址。
- 认证文件采用受限权限挂载；密码/token 不进入 CLI 参数、任务 JSON、预览、日志或 API 响应。
- 不同邮箱不得共用 OAuth token store 路径；发件账号与授权实际账号不符时拒绝发送。
- 不继承另一个邮箱的 SMTP、OAuth 或 IMAP 凭证；缺失必要配置失败关闭。保持生产 TLS 校验。
- mailbox_id 对应的发件地址不可原地改成另一邮箱；需要新身份时新增 ID，旧任务仍保留原身份。
- 默认发送间隔仍为 5 秒，同一邮箱所有 API/Worker/重试共享发送锁，两个执行位不绕过该间隔。
- 延续当前 email:send scope 与 token 所有权隔离；本期不新增组织/角色管理系统。两个 Agent 可使用独立访问 token，不能越权读取或启动对方任务；共用 token 则按现有同一所有者语义处理。

## 4. 任务、预览与模板绑定

新建批次和单封预览增加 mailbox_id。数据库持久绑定邮箱；冻结的发件地址、显示名称、模板 ID/版本、正文和图片属于确认内容。幂等指纹和审批 revision 包含邮箱选择；同一幂等键对应不同邮箱/模板时返回冲突。

- 同一任务的读取、批准、执行与退信重试始终解析绑定邮箱，不能回退到默认邮箱。
- 修改发件身份或确认内容需新建预览/批次并重新确认。凭证正常轮换不要求改动正文或重复创建发送尝试。
- 邮箱禁用、授权失效、限流或退信暂停只影响其自身任务；无自动切换邮箱重发。
- 发送 Worker 除队列隔离外，再校验任务 mailbox_id；错投队列不能导致发信。
- 模板选择与邮箱配置的允许列表一致。LIMINAL 模板最初仅允许现有 ontologyplay 邮箱，避免固定签名与另一发件邮箱不符；第二邮箱的模板需配置后才能使用。
- 发送前重新校验身份与模板许可，配置不匹配则阻止发送，不静默修改冻结内容。
- API/任务列表/轻量状态查询返回 mailbox_id、发件地址、模板版本与对应安全状态，不加载大体积内联图片来汇总进度。

## 5. CLI、页面与 Skill

新增只读邮箱发现命令 fmg email mailboxes，返回可选择的邮箱别名、发件地址、可用性及允许模板，不返回凭证或内部文件路径。

在现有 fmg outreach task create --input FILE --idempotency-key KEY 基础上新增 --mailbox、--template、--template-version；JSON 也可包含 mailbox_id、template_id、template_version。两处同时指定且不一致时拒绝，不静默覆盖。真实模板 ID 使用现有 liminal-outreach / game-outreach，不将之前示例中的 liminal 当作真实 ID。

单封预览同样明确 mailbox_id。新 CLI 要求指定邮箱，模板及版本须来自明确输入，不自动选择“第一个”。后端仅在单一兼容邮箱模式允许旧客户端省略 mailbox_id；启用多邮箱后省略返回 mailbox_selection_required。旧的已绑定任务仍可按 ID 查询和启动，但仍需原审批和安全检查。

页面显示邮箱、显示名称、模板 ID/版本、收件人数与原稿；保留不展示 Reply 的既有决定。Skill 指导 Agent 先查询可用邮箱及模板，明确选择、预览、获取发送确认，再创建/启动；失败或 unknown 不自动换邮箱。

CLI 和 Skill 同一版本发布，兼容性检查明确提示旧客户端更新。文档命令以实现后的 help/API 目录验证，不发布仅存在于方案中的语法。

## 6. 收信、退信与防重复

每邮箱独立 IMAP 授权、文件夹游标和监控健康状态。收到邮件时，除现有 Message-ID/References/发件人匹配，还校验原发送所属邮箱，防止另一个邮箱的转发邮件或同一 UID 串账。

退信重试从原 preview/send 继承 mailbox_id 和冻结内容，投递到所属邮箱队列。保留当前一次重试、30 秒等待、失败阈值、无效地址排除和暂停机制，不重新解释或重置历史计数。unknown 不自动重发；已 sent 的发送尝试不因重复任务消息再次调用上游。

请求幂等和发送锁防止同一任务重复执行，不承诺不同 Agent 在不同任务中给同一联系人发送同样内容时会自动去重。本期不新增跨批次拦截；CLI/Skill 明确要求划分名单，避免用户误以为“两个任务”会自动视为同一封。

## 7. 迁移和部署边界

- 本地实现和自动化测试不访问真实 Gemini，不实际发邮件，不启动用户已停用的本地 FMG Docker 服务。
- 历史预览按冻结 from 精确映射到现有邮箱；同批次出现混合或无法映射的身份须停止迁移并报告，不猜测归属。
- 不改变历史正文、图片、receipt、审批 revision、幂等键、暂停状态；仅添加可验证的身份关联。历史尚未发送任务不能因此自动获得批准。
- 使用增量数据库迁移并提供只读迁移预检、迁移前后数量/摘要核对。
- 发布先备份数据库和私有配置。暂停旧任务调度，在途发送温和排空后切换；不能依靠 API 进程清闲推断没有在途发送。
- API 单封发送也须纳入切换闸门。不能强杀正在提交邮件的进程；排空超时则停止发布并报告。
- 旧 Redis 队列中的过期/未确认任务必须按 DB 中原审批、状态与幂等性审计后迁移，不能盲目清空队列或全部重放。
- 上线完成前不恢复历史暂停批次、不解除邮箱保护、不触发新付费检索或测试邮件；第二个真实邮箱接入需用户另行提供配置和授权。
- 回滚保留新增身份数据；若第二邮箱已有任务，不直接启动不识别 mailbox_id 的旧 Worker。先阻止调度，再采用支持身份绑定的版本修复或回滚。

## 8. 验收测试（必须包括两个 Agent）

所有并发/锁验证使用真实 PostgreSQL/Redis 隔离测试实例及虚拟 SMTP/Graph/Gemini；SQLite 单元测试不能代替共享锁测试。集成环境不可用时明确报告未验证，禁止声称已通过。

1. 两个 CLI 使用不同 token 同时创建/启动各自批次，读取与批准所有权隔离，不能跨 token 越权。
2. 两个 CLI 共用 token、同幂等键同时提交相同请求，只创建一个任务；不同内容或邮箱则冲突。
3. 同一批次并发 start、同一预览使用不同发送键重复提交及队列重复投递，上游最多调用一次；unknown 无额外调用。
4. 同邮箱两 Agent 的正常发送与退信重试共用锁，间隔至少 5 秒；不存在各自节流造成总速率翻倍。
5. 不同邮箱发送可重叠，凭证/From/回执/模板完全独立；A 限流、无效配置或退信暂停，B 正常推进。
6. 四个慢 Gemini 任务占满补全执行位时，已批准邮件仍能执行；补全异常不占据发信 Worker，检索预算和失败策略不变。
7. A 收信连接阻塞或失败时 B 仍能扫描；相同 UID、跨邮箱引用及转发消息不串账。
8. 重试路由、邮箱禁用、模板许可变更、授权账号不符及错误队列均失败关闭，不切换身份。
9. 历史任务迁移与新旧 CLI 兼容规则；大批次 summary 保持小响应；LIMINAL 正文与两张图片回归不变。
10. 调度器仅单实例生效；Worker 重启/任务过期/排空超时的恢复不漏任务、不新增重复发送。
11. UI/JSON/日志/错误不泄露凭证；CLI 输入与 flags 冲突明确报错；Skill 示例与实际 help 一致。
12. 对新 Worker 组合进行受控虚拟负载验证，记录内存、CPU、DB 连接、邮件等待时间和队列积压；再决定是否具备生产切换条件。

## 9. 完成定义和下一阶段

设计确认后编写逐项实施计划，再进行 TDD 实现、全套回归与发布准备。完成交付必须区分“本地测试通过”“已发布 CLI/Skill”“已部署服务器”“第二邮箱已授权可用”，不将其中一项等同于全部完成。

初期不增加 Gemini 到 6–8 并发，不增加新发信供应商 SDK，不自动为第二邮箱生成新营销模板，不绕过服务商额度和反垃圾限制。
