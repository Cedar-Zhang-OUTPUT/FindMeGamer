# SMTP Sent copies

User approved saving accepted SMTP mail to the sending mailbox's Sent folder,
without conflating provider acceptance, archive completion, or actual delivery.

## Contract

- Private mailbox fields: `smtp_save_sent_copy` (default false) and
  `imap_sent_folder` (default `Sent`). Enable only for `second`.
- Graph is unchanged; its provider already saves Sent items.
- SMTP acceptance is committed before IMAP is contacted. The receipt stays
  `sent` even when storage fails. No storage outcome authorizes a new SMTP send.
- `diagnostics.sent_copy.state`: pending, saved, already_exists, failed, unknown.
  Unknown means an APPEND acknowledgement was lost. Never automatically append
  again or resend. The ordinary send idempotency key still returns the old receipt.
- The append targets the selected mailbox's own TLS/password IMAP account.
  The explicit existing Sent folder is examined read-only, then Message-ID is
  searched before APPEND with Seen. No folder creation, expunge or inbox flag change.
- Pending receipts can survive process/DB failure. An administrator can explicitly
  call `archive_sent_copy(sessions, send_id, selected_settings)` to reconcile/repair.
  It only accepts `sent` rows with the matching sender and serializes on the send
  row in PostgreSQL. It does not call SMTP.
- For new archive-enabled sends, the durable reservation date, send ID and
  immutable preview reproduce identical MIME bytes on repair, including images.
  Older sends predate this convention: reconstructed copies preserve content and
  Message-ID but cannot prove their original MIME bytes/date. Supply the verified
  original `.eml` as `raw` when doing a specifically authorized historical import.
- Folder configuration currently supports printable ASCII IMAP names, quoted
  safely; OAuth IMAP storage is not supported. The Graph mailbox is unaffected.
- MIME bytes and provider error strings are never included in public diagnostics.
  `sent` still does not mean inbox placement or receipt by the human recipient.

## Rollout / rollback

Use two minimal derivatives: five API/mail roles based on the current
`thieves-footer-20261020` image; enrichment based on its current
`gemini429-20261020` image, copying only config/registry compatibility.
Older strict registry readers cannot accept the new fields: warm-stop all six
roles and update schema readers before enabling the second mailbox's fields.
No Gemini logic, credentials, safety holds, templates or historical send states
are changed.

Before cutover, preserve private runtime/registry/image metadata. Require no
active sends, bounce retry work, unfinished outreach recipients, or active
enrichment jobs. Hold mail runtime gates; warm-stop without forced killing.
Verify all roles' exact image IDs, registry isolation, role readiness and unchanged
send counts before restoring prior runtime flags. If an unexpected live job
appears or health fails, stop and investigate rather than force through.
Rollback restores the previous registry before restoring the old images.

## Validation

Initial regression tests observed 6 failures for missing save/error/dedup/isolation
behavior and 2 passing negative-path tests. Review found nonidentical repair MIME;
a new rejection-then-repair test reproduced that issue and passed after making
serialization deterministic. Independent re-review: 81 focused tests passed,
no remaining findings. Full-suite and live results are recorded after execution.

Full regression on the final implementation: 591 passed, 1 skipped in 666.13s.
This included real isolated local PostgreSQL/Redis role, pacing, restart and
dual-mailbox resource tests. The optional container backup/restore rehearsal was
skipped because `FMG_AGENT_TEST_IMAGE` was not set; it is not claimed as exercised.
The new production derivatives were separately built and validated offline
(`--network none`), including source hashes and deterministic No Rest MIME.

DNS was configured by the user: `_dmarc` TXT `v=DMARC1; p=none`.
Public DNS confirms it. Original recipient EML verifies DKIM cryptographically
and SPF for the recorded provider egress IP. That is not proof of the recipient's
historical authentication decision or a promise of future inbox placement.
