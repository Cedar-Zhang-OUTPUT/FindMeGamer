# Research decisions

1. Resolve the Steam URL's App ID, or use `store.search` and clarify genuine identity ambiguity before describing a particular game. Fetch `store.appdetails` and `store.recommendations`. Recommendations' `name_hint` is not an official title; inspect relevant IDs' details. Create a draft `game-profile.md`: metadata, concise summary, gameplay, loop, audience/style inferences, related games, references and retrieval time. Separate supported facts, Agent inferences and unknowns. Keep this campaign's intent separate from game facts.
2. Draft search intent as hard constraints, preferences and derived leads. Inspect supported YouTube/X/Twitch operation schemas to identify which constraints can be API filters and which require evidence-based screening later; do not run discovery yet. Compare creator country, content language and audience geography separately. Unknown hard-constraint data does not pass a hard filter; propose a needs-verification group, not silent relaxation. All-platform discovery means these three supported providers; Instagram remains unavailable except for user-supplied evidence. Use the main Skill's 10-per-selected-platform default only when no count is specified. **Complete the game-review gate below before proceeding.**
3. After explicit approval of the game understanding and search plan, translate the agreed intent into supported queries and start finite targeted searches, including approved related-game/synonym angles. Save each page before requesting another. Extract stable author account IDs, not post IDs or display names. Consult `creator-index.json` before deeper calls. For 'find new people', exclude every previously seen account, not merely recommended accounts. Same display name across platforms is not identity. If the user changes criteria or asks for reevaluation, keep prior events and explicitly record a new decision.
4. Inspect promising authors' public profile/metrics and a bounded sample of works. Batch IDs where supported. Load small summaries into context, return to raw files for evidence. A video title/description/thumbnail supports only what it shows; it is not proof of watching an entire video or of actual gameplay. Record work URL/date, observed content and evidence level. Playing a related game is a strong match signal when supported; otherwise assess audience, genre/style and requested preferences.
5. Complete default public business email lookup for each suitable result per the main Skill and outreach reference. Save pending jobs immediately, poll existing jobs, and update contacts atomically; do not wait for a separate email request.
6. Write JSON Match Briefs for suitable candidates using the file contract. Explain why selected and what remains uncertain; keep discovery paths and exact source references. Do not save hidden internal deliberation. Avoid flattening evidence-supported matches and speculative leads into one list.

Resume from `progress.json`, the confirmation record and saved artifacts. An interrupted approved run can continue within its unchanged scope without another identical question; a missing/pending confirmation cannot. For a new 'find more' run, briefly restate the previously confirmed understanding and ask approval of the continuation scope unless the user has explicitly requested continuation of that exact saved plan. Material changes to game identity, gameplay interpretation, campaign angle, hard constraints, platforms or budget require presenting the revision for confirmation before affected searches. Routine query phrasing/cursor changes within approved angles do not need a new approval. Repeat only missing/failed reads or deliberately refresh stale evidence; keep successful work. Public data changes: record retrieval dates and respect provider retention/deletion requirements rather than treating saved API content as permanently current. New task budgets are finite even if an older run found too few results.

## Game-review gate

Before the first creator search, give the user a useful, detailed briefing in the conversation, not just a saved file or “Is this game correct?”:

- **Game identity and sources:** title, Steam URL/App ID, developer/publisher and relevant release status when available. Resolve ambiguous titles rather than choosing silently.
- **Game understanding:** genre/subgenre, main mechanics, game loop, single/multiplayer context, pacing, visual/narrative tone, and likely appeal. Explain audience and creator-fit interpretations separately from sourced facts. State missing information and source limitations; Steam tags alone are not proof of a mechanic or audience.
- **Proposed discovery angles:** which distinctive mechanics, themes, formats, game name and related titles would drive discovery, why each angle is relevant, and which broad/misleading associations to avoid. Give representative query examples grouped by platform/angle; no need to dump every future API parameter. Steam recommendations are candidate leads, not proof of equivalent gameplay.
- **Filters and scope:** requested languages, regions, follower ranges and keywords; explain API filtering versus later screening, unknown evidence, selected platforms, target counts, request ceilings and known/unknown costs. Preserve explicit user constraints.
- **One clear confirmation:** use the bundled interactive game/filter page in Codex's built-in browser, with current defaults prefilled; see [interactive review](game-review.md). Explain the game and proposed search angles there, and invite corrections. Saving approves the displayed plan plus chosen filters/corrections, not sending. If a browser is unavailable or the user prefers conversation, use Codex's question interface with the same scope, never terminal `input()`. Do not ask for information already supplied.

While waiting, set `awaiting_game_confirmation` and preserve the draft Profile and Search Intent. Steam reads needed to understand the game and local preparation are allowed; platform creator searches, creator-detail calls and email enrichment for this discovery task are not. Do not run them in a background task while awaiting the user. If the turn ends, record the Steam calls/cost snapshot already incurred rather than claiming zero work.

If the user corrects the interpretation, record their correction separately from Steam-sourced facts, update the proposed intent, and show the revised summary. Proceed only when the user approves that revised direction; “focus on puzzles instead, then go ahead” is approval of that specified correction, but a bare correction or unrelated reply is not. If Steam details conflict with the user, explain the discrepancy rather than laundering the correction into an API fact. Unknowns may remain unknown if the user explicitly accepts the limited basis. The approved search scope includes default contact lookup for suitable matches, not enrichment of every raw search hit, exceeding limits or sending emails.

Examples of expected handling:

- “Find 30 creators for this Steam link” → Steam facts/Profile, game/search briefing, then await approval; no YouTube/X/Twitch discovery yet.
- “It is not primarily combat; emphasize exploration” → revise understanding and proposed leads, ask whether to proceed; do not retain combat as a core angle silently.
- “Correct, use those angles and continue” → record approval and start bounded discovery.
- Resume after interruption → read the saved approval and actual completed steps; do not invent approval or repeat already completed requests.

For Twitch, resolve the game or related games to Twitch category IDs using `getGames`/`searchCategories` (Steam App IDs are not Twitch category IDs). Inspect `getStreams` for current broadcasts and `getVideos`/`getClips` for works; a channel-name search alone does not establish game affinity. Extract broadcaster/user IDs, not clip creator IDs, and deduplicate before detail reads. `getUsers`, `getChannelInformation` and `getChannelFollowers` supply profiles, current category/language and follower totals. A live viewer count is not followers; a current category is not complete play history. Video-by-category returns at most 500 videos, not 500 unique creators; do not promise exhaustive discovery. Preserve per-platform target, page and result counts in progress. API email absence is expected: use default public business contact enrichment for suitable matches, not a request for another creator's private account permissions.

## Show creator results

As soon as the first evidence-backed creator result is saved (not merely a raw search hit), launch the bundled results dashboard in a retained terminal session:

```sh
python3 PATH_TO_INSTALLED_FMG_RESEARCH/scripts/research_dashboard.py --root WORKSPACE --run-id RUN_ID
```

Open its exact printed loopback URL in Codex's built-in browser. It reads saved Match Briefs every five seconds without provider calls, shows all nine required result columns with actual email addresses (not just lookup status), 20 creators per page, and supports search, platform/decision filters and evidence details. Continue writing valid briefs atomically while the user reviews. Do not wait until all contact lookups finish. The dashboard links to canonical profiles and evidence; open the specific creator's profile when requested. A later rejection/correction must remain visible in saved results, not silently disappear.

For subsequent results, preserve the user's current view rather than opening dozens of tabs or navigating away while they read. Reuse the results dashboard, keeping JSON Match Briefs and requested Excel deliverables in parallel; browser display is not a replacement for saved evidence. This local viewer is separate from the server-backed outreach dashboard. It never approves research, edits saved data or sends email.

Use the host's actual built-in browser capability and verify the returned page/state before saying it is open. An operation queued to a hidden panel is not proof the user sees it; provide its link as a fallback. Do not make another provider API call just to open an already known link, do not bypass login/security barriers, and do not infer watching a full video from opening its page. User feedback may revise the search direction under the game-review gate. Opening a page alone does not impose an extra approval stop on otherwise approved research.
