# Research decisions

1. Resolve the Steam URL's App ID, or use `store.search` and confirm genuine ambiguity. Fetch `store.appdetails` and `store.recommendations`. Recommendations' `name_hint` is not an official title; inspect relevant IDs' details. Create `game-profile.md`: metadata, concise summary, gameplay, loop, audience/style inferences, related games, references and retrieval time. Separate supported facts, Agent inferences and unknowns. Keep this campaign's intent separate from game facts.
2. Write search intent as hard constraints, preferences and derived leads. Translate to supported YouTube/X/Twitch queries after `describe`; do not assume every user constraint is a native API filter. Compare creator country, content language and audience geography separately. Unknown hard-constraint data does not pass a hard filter; place such candidates in a needs-verification group. Do not silently relax filters. All-platform discovery means these three supported providers; Instagram remains unavailable except for user-supplied evidence. Verify gateway operation availability before promising results. Use the main Skill's 10-per-selected-platform default only when no count is specified.
3. Start with finite targeted searches, including relevant games/synonyms where useful. Save each page before requesting another. Extract stable author account IDs, not post IDs or display names. Consult `creator-index.json` before deeper calls. For 'find new people', exclude every previously seen account, not merely recommended accounts. Same display name across platforms is not identity. If the user changes criteria or asks for reevaluation, keep prior events and explicitly record a new decision.
4. Inspect promising authors' public profile/metrics and a bounded sample of works. Batch IDs where supported. Load small summaries into context, return to raw files for evidence. A video title/description/thumbnail supports only what it shows; it is not proof of watching an entire video or of actual gameplay. Record work URL/date, observed content and evidence level. Playing a related game is a strong match signal when supported; otherwise assess audience, genre/style and requested preferences.
5. Write JSON Match Briefs for suitable candidates using the file contract. Explain why selected and what remains uncertain; keep discovery paths and exact source references. Do not save hidden internal deliberation. Avoid flattening evidence-supported matches and speculative leads into one list.

Resume from `progress.json` and saved artifacts. Repeat only missing/failed reads or deliberately refresh stale evidence; keep successful work. Public data changes: record retrieval dates and respect provider retention/deletion requirements rather than treating saved API content as permanently current. New task budgets are finite even if an older run found too few results.

For Twitch, resolve the game or related games to Twitch category IDs using `getGames`/`searchCategories` (Steam App IDs are not Twitch category IDs). Inspect `getStreams` for current broadcasts and `getVideos`/`getClips` for works; a channel-name search alone does not establish game affinity. Extract broadcaster/user IDs, not clip creator IDs, and deduplicate before detail reads. `getUsers`, `getChannelInformation` and `getChannelFollowers` supply profiles, current category/language and follower totals. A live viewer count is not followers; a current category is not complete play history. Video-by-category returns at most 500 videos, not 500 unique creators; do not promise exhaustive discovery. Preserve per-platform target, page and result counts in progress. API email absence is expected: use public business contact enrichment when needed, not a request for another creator's private account permissions.

If the user wants to view a creator, open the saved canonical profile URL with Codex's available browser capability. Do not make an API call just to open a link. If the browser tool is unavailable, provide the link without claiming it was opened.
